## Part 1 – Load Word Indexed

Encoding `0000000 rs2 rs1 010 rd 0101011`, `rd = mem[rs1 + rs2]`. It is an
R-format instruction (two source registers, like `add`) that performs a load
(like `lw`), so it is decoded with `Format_R` and executed with the `lw` load
path on the address `REG_GET(0) + REG_GET(1)`. The lab's assembly uses it as
`.word 0x00F727AB` = `lwi a5, a5(index), a4(base)`, replacing
`add a5,a4,a5` + `lw a5,0(a5)`; the index was already scaled by 4 with `slli`.

| | cycles |
|---|---|
| Baseline (original ISA) | **277,398** |
| Modified (with `lwi`) | **268,182** |
| Difference | **9,216 fewer (−3.3 %)** |

`check-image-blur-modified` prints **"LWI implemented correctly"**;
[output_image.png](results/output_image.png) is the blurred
[original.png](results/original.png).

**Q: What is the difference in cycles?** 9,216 cycles. The image is 32×32 =
1,024 pixels and the 3×3 blur does 9 loads per pixel. Each load used to be
`add` + `lw` and is now a single `lwi`, so each one saves one instruction:
1,024 × 9 = 9,216. The memory access itself is unchanged; only the address
addition is merged into the load. Most of the loop is still index
arithmetic, so the overall gain is a modest 3.3 %.

## Part 2 – Multi-core

- `my_system.py`: 16 `rv64imafdc` cores with `core_id` 0–15 (core 0 keeps
  the name `host`, because the plot scripts trace `host/insn`). Each core has
  fetch/data/debug ports on the interconnect, and the loader drives every
  core's `FETCHEN`/`ENTRY`. `Global_Mem` is mapped at `0x20000000`, size
  `0x1000`.
- `main.c`: each core takes a contiguous slice of
  `ceil(arr_size / NUM_CORES)` elements and counts its 3s. It writes its count
  to `global_mem[core_id]`. Cores other than 0 then pause. Core 0 waits until
  no counter is still −1, adds them up, prints, and writes `sync = 0` to
  release the others. Cores with `core_id >= NUM_CORES` write 0 and pause
  immediately.

`make gvsoc verify` → **All tests were passed!!** (1–16 cores × arrays 1, 2, 3;
[log](results/p2_verify.log)).

### Array 1 – [plot](results/p2_plot_array1.png)

| cores | 1 | 2 | 4 | 8 | 16 |
|---|---|---|---|---|---|
| cycles | 35,164 | 19,177 | 11,234 | 7,406 | 5,790 |
| speedup | 1 | 1.83 | 3.13 | 4.75 | 6.07 |
| efficiency | 1 | 0.92 | 0.78 | 0.59 | 0.38 |

**1. Why is the graph non-linear?** Only the counting loop is divided
between the cores; everything else is not:

- **Serial code:** start-up, the final sum and above all the `printf` run on
  core 0 only. The `printf` alone takes about 2,900 cycles (measured from the
  trace). That is ~8 % of the 1-core time and already half of the 16-core
  time.
- **Overhead that grows with the core count:** `sync_cores()` and the final
  sum both loop over `NUM_CORES`. Core 0 spends 91 cycles in sync on 1 core
  and 800 cycles on 16 cores.
- **Load imbalance:** core 0 has to wait for the slowest slice. A slice with
  more 3s does more increments, and the last slice can be shorter.

So the run time behaves like `T(N) ≈ T_serial + T_parallel/N + c·N`. That is
a hyperbola flattening out toward `T_serial`, not a straight line.

**2. Amdahl's law.** Take N = s = 16, S = 35,164 / 5,790 = 6.07:

```
1/S = (1 − p) + p/16   →   p = (1 − 1/S) / (1 − 1/16) = (1 − 0.1647) / 0.9375 ≈ 0.89
```

So **about 89–90 % of the program is parallelisable** and the rest is serial.
The other points give a similar result: 2 cores → 0.909, 4 → 0.907,
8 → 0.902. A least-squares fit of `T(N) = T_serial + T_parallel/N` over all
16 points gives p = 0.897, with a serial floor of about 3,600 cycles.
The trace agrees: on 1 core the counting phase takes 32,188 of the 35,164
cycles, about 91 %. The estimate drops slightly as N grows because the sync
overhead grows with N, which Amdahl's law does not model.

**3. Beyond 16 cores?** The curve keeps flattening. With p ≈ 0.89–0.90 the
speedup can never go past 1/(1−p) ≈ 9–10× (≈ 3,600–3,800 cycles), however
many cores are added. Before getting there, the per-core overhead (sync and sum loops,
+c·N) starts to outweigh the shrinking slices (1000/N elements). The curve
then reaches a minimum and **rises again**, like Array 3 already does. Going
past 16 would also need a bigger `global_mem` (it holds 16 counters).

### Array 1 vs Array 2 – [plot](results/p2_diff.png)

Difference (Array 1 − Array 2) per core count:
317, 273, 243, 235, 225, 221, 219, 219, 219, 215, 213, 211, 211, 211, 211, 211.

**1. What differs in execution?** Same size and same loop. In Array 1,
`if (arr[i] == 3)` is true 56 times, so `local_counter++` (load, add, store)
runs 56 extra times. In Array 2 it never does. The final `printf` also
prints "56" instead of "0", which needs one more digit to format. From the
trace, the difference splits into:

- **printf:** a constant 205 cycles at every core count.
- **counting:** about 2 cycles per 3 on the critical path. On 1 core that's
  112 cycles (56 threes); on 16 cores only 6–14 cycles.

**2. Why does the difference decrease? Will it reach zero?** The 3s are split
between the cores. Core 0 only waits for the slowest core, so only the 3s in
that core's slice count. That's 56 on 1 core, 34 on 2, 19 on 4, 11 on 8 and
7 on 16. **It will not reach zero.**

- A core whose slice still contains 3s will always be on the critical path;
  its cost only tends to zero, scaling with max 3s per slice ≈ 56/N.
- The `printf` cost does not depend on the core count. That's why the curve
  levels off at about 211 cycles instead of going to 0.

**3. More occurrences in Array 1?** The difference grows by about 2 cycles
for every extra 3 that lands in the busiest slice. On 1 core all of them
count, so the gap grows linearly with the number of 3s. With more cores each
extra 3 adds only ~1/N as much, so the curve starts higher but still falls
toward the `printf` floor. If the count needs another digit (≥ 100), that
floor goes up by roughly another ~200 cycles. Clustered 3s cause load
imbalance and make the gap shrink more slowly than evenly spread ones.

### Array 3 – [plot](results/p2_plot_array3.png)

Cycles: 4,224 (1), 3,693 (2), 3,576 (3), **3,494 (4)**, 3,537, 3,520, 3,567,
3,550, 3,594, 3,641, 3,688, 3,703, 3,750, 3,797, 3,844, 3,862 (16).

**1. Why is the trend different?** Array 3 has only 36 elements, so the work
that can be divided is tiny: roughly 1,100 cycles of counting. It is small
next to the fixed serial part (`printf` and start-up) and the per-core
overhead (~40 cycles per extra core for `sync_cores` and the sum loop).

- Going from 1 to 4 cores the counting work shrinks faster than the overhead
  grows, so time drops.
- After that, each extra core saves almost nothing (2–3 elements) but still
  adds its sync and sum overhead, so time **rises** linearly. The small zigzag
  comes from 36 not dividing evenly by N.

Array 1 has 1,000 elements, so its curve is still in the falling part at
16 cores.

**2. Ideal number of cores?** **4 cores** (3,494 cycles, a speedup of 1.21×).
5–6 cores are almost the same. Using `T(N) ≈ T_s + W/N + c·N` with
W ≈ 1,100 and c ≈ 40, the minimum is at N = √(W/c) ≈ 5, which matches the
measurements.

## Bonus – character histogram – [plot](results/bonus_plot.png)

Same scheme as Part 2:

- Each core builds a 7-bin histogram of its slice and stores it at
  `global_mem[core_id*NUM_BINS .. +6]`.
- `sync_cores` checks `NUM_CORES*NUM_BINS` words, and core 0 adds the partial
  histograms bin by bin.
- Unused cores only clear their own 7 words. `global_mem[core_id]` would
  overwrite a used core's bins.
- The global memory has 16 × 7 = 112 counters.

Big test string, 16 cores:

```
Bin[0]: 500  Bin[1]: 500  Bin[2]: 600  Bin[3]: 1000  Bin[4]: 1000  Bin[5]: 100  Bin[6]: 100
```

This matches the expected output, and I checked it for every core count from
1 to 16. Cycles go from 272,198 on 1 core to 46,171 on 16 cores, a 5.9×
speedup.
